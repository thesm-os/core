# How to generate the conformance suites

[dokimi][dokimi] generates the test doubles, the conformance suites, the builders
and the sentinel tests of core from directives in doc comments. The
[Go guide of dokimi][dokimi-go] describes each directive. This guide covers how
core places, writes and applies the generated files.

Do not edit a file that opens with `// Code generated by dokimi. DO NOT EDIT.`
Change the directive that writes it, and run `make generate`, which runs dokimi
and then kanon. `make check` runs `verify-generate-go`, which fails when a
generated file differs from the output of its directives. `.dokimi.yaml` sets
`strict: true`, so a warning of dokimi fails both targets.

## Place the directives

- Put `//dokimi:stub` and `//dokimi:suite` in the doc comment of an interface, in
  its production package. Add `//dokimi:out` with the path of its kit, relative to
  the package, as `crypto/mac.go` does:

  ```go
  //dokimi:stub
  //dokimi:suite
  //dokimi:out path=../coretest/cryptotest/
  type MAC interface {
  ```

- Write the files of an interface of a subpackage into the kit of its parent
  package. The interfaces of `crypto/sign` take
  `path=../../coretest/cryptotest/`.
- Find a generated file by the name of the source file of its declaration.
  `id/generator.go` gives `generator_stub.go` and `generator_suite.go` in
  `coretest/idtest`, and a spec of each.
- Put `//dokimi:sentinel` at the end of the package comment, as `cache/doc.go`
  does. It writes `errors_sentinel_test.go` beside the sentinels.
- Put `//dokimi:builder` and `//dokimi:out` on a struct whose values a kit builds,
  as `clock.Instant` has.

## Write a check of a suite

Write each law of a suite as a function of the kit with a `//dokimi:check`
directive. Open its doc comment with `<Name> checks that` and the statement of the
law. Pass `h.Statement()` as the message of the assertion of the law. The checks
of `coretest/idtest/generator.go` follow this form:

```go
// ReturnsNonZero checks that Generate does not return the Zero ID.
//
//dokimi:check Generator.Generate defect=returnsZero
func ReturnsNonZero(h *GeneratorHandle) {
	assert.False(h, h.Subject().Generate().IsZero(), h.Statement())
}

// returnsZero returns the planted defect of ReturnsNonZero and ReturnsDistinctIDs: a
// Generator whose Generate returns the Zero ID on every call.
func returnsZero(h *GeneratorHandle) id.Generator {
	return NewGeneratorStub(h, WithGeneratorGenerate(func() id.ID { return id.Zero }))
}
```

- Give each check a planted defect. The defect is a function of the kit that
  returns a double whose calls break the law. `ReturnsNonZero` and
  `ReturnsDistinctIDs` share `returnsZero`, because it breaks both laws.
- To check a law over generated inputs, take a `*prop.Case` as the second
  parameter and call `c.Draw` for each input.
- If a check calls `h.Reference`, `h.Second`, `h.Restart` or `h.Crash`, give its
  defect the same door with `reference=`, `second=`, `restart=` or `crash=`.
- If two suites of core declare an interface of the same name, name the package in
  the directive, as in `//dokimi:check cas.Store.Get defect=<defect>`.
- Run the tests of the kit. `Test<X>Suite` falsifies each check. A defect must
  fail its own check at the assertion of its statement and pass every other check
  of the suite.

## Apply a suite to an implementation

Put `//dokimi:subject` on the type of the implementation. `new` names a factory
without parameters in the test package, and `options` names a function that
returns the options of the suite, as `cas/memory` does:

```go
//dokimi:subject cas.Store new=newStore options=storeOptions
type Store struct {
```

```go
func newStore() *memory.Store {
	return memory.New(sha256.New())
}

func storeOptions() []castest.StoreOption {
	return []castest.StoreOption{
		conform.Restartable(func(_ *castest.StoreHandle, s cas.Store) cas.Store { return s }),
		conform.Crashable(func(_ *castest.StoreHandle, s cas.Store, call func()) cas.Store {
			call()

			return s
		}),
	}
}
```

dokimi writes `Test<Type>ConformsTo<X>`, a benchmark of each method and a fuzz
target of each method into `<file>_suite_test.go` beside the test of the type.

- To set an allocation ceiling, add `//dokimi:budget X.Method allocs=<n>` after
  the `subject` directive, as `crypto/hmac/sha256/sha256.go` does. A budget adds
  `Test<Type>ConformsTo<X>Allocs`.
- If the implementation does not keep a law of the suite, excuse its check with
  `//dokimi:excuse X.Method/<check> reason="<reason>"`, as `id/constant` does.
- Pass the reference of a MAC with `conform.Reference`, and a second subject with
  `conform.Second`.
- If the constructor returns an error, or the type is unexported, apply the suite
  in a hand-written test with `Run<X>SuiteFromHandle`, as
  `crypto/aesgcm/aesgcm_test.go` does.

## Configure a test double

`New<X>Stub(tb, options...)` returns a double with a field `On<Method>` for each
method:

- `Returns` fixes the results of the method, and `Func` computes them.
- `Faults` fails every nth call with an error. `FaultsOnce` fails the next call
  and `FaultsFor` fails the calls of a duration.
- `Latency` delays each call. `Times` sets the number of calls that the test
  expects.
- `<X>StubStrict()` fails the test on a call of a method that the test did not
  configure.
- `<X>StubDelegateTo(impl)` passes each call to an implementation.
- `With<X><Method>(fn)` sets the function of one method when the double is built.
  The planted defects of the kits use it.
- `<X>StubWithClock(clk)` sets the clock of the latency and of the windows of the
  faults. A latency on a controlled clock costs no real time.

## Mark a method of an interface

Put `//dokimi:mixin concurrent` on a method that is safe for concurrent calls,
such as `MAC.Sign`. The application of the suite then also benchmarks the method
on `GOMAXPROCS` goroutines at once.
