# RFC-0009: ID — 128-bit Identifier Seam

## Summary

A fixed-max-size `ID` value type covering 128-, 160-, and
256-bit identifier shapes in a single comparable type, plus a
`Generator` interface with four concrete generator subpackages:
`id/ulid` (128-bit time-sortable ULID), `id/uuidv4` (128-bit
random UUIDv4), `id/ksuid` (160-bit K-sortable UID), and
`id/fixed` (constant for fixtures). Each subpackage ships
`Format` and `Parse` for canonical serialization. The seam
composes with `core/clock` and `core/rand` so generators are
concrete and consumer-injectable.

## Motivation

Every consumer that mints request, trace, entity, or
idempotency identifiers either binds to a specific library
(forcing every test to deal with non-determinism and every
consumer to ship the same dependency) or rolls their own. The
identifier shape is universal — 128 bits covers both production
identifier formats — but the generator layer is not.

Promoting the seam into core gives every consumer:

- One value-type for storage layouts, comparisons, and
  serialization.
- One injection point where production wires `clock.Clock` +
  CSPRNG-grade `rand.Rand`, tests wire `clock/fake.Clock` +
  `rand/seeded.Rand` for reproducible streams.

## Detailed design

```go
const (
    Size128 = 16
    Size160 = 20
    Size256 = 32
    MaxSize = Size256
)
type ID struct { ... }  // [MaxSize]byte + uint8 size tag
var Zero = ID{}

func New128(b [Size128]byte) ID
func New160(b [Size160]byte) ID
func New256(b [Size256]byte) ID

func (ID) Size() int
func (ID) Bytes() []byte
func (ID) IsZero() bool
func (ID) Equal(other ID) bool
func (ID) Compare(other ID) int
func (ID) String() string

type Generator interface {
    Generate() ID
}
```

Four subpackage implementations:

- **`id/ulid`** — Crockford-base32-encoded 128-bit ULID
  (48-bit ms timestamp + 80 random bits). Time-sortable;
  bytewise lexicographic order matches generation order at
  millisecond granularity. Depends on `clock.Clock` +
  `rand.Rand`. Ships `Format` / `ParseULID`.
- **`id/uuidv4`** — RFC 4122 UUID v4 (122 random bits + 4
  version bits + 2 variant bits). Non-sortable. Depends on
  `rand.Rand` only. Ships `Format` / `Parse`.
- **`id/ksuid`** — base62-encoded 160-bit K-sortable UID
  (32-bit Unix-second timestamp since the KSUID epoch +
  128 random bits). Time-sortable at second granularity.
  Depends on `clock.Clock` + `rand.Rand`. Ships
  `Format` / `Parse`. Selected when consumers want longer
  entropy than ULID provides or alphanumeric-only encoding.
- **`id/fixed`** — constant-output generator for fixtures and
  deterministic tests.

### Three sizes in one type

[ULID](https://github.com/ulid/spec) and UUIDv4 are both 128
bits. KSUID is 160 bits. Hash-derived identifiers (SHA-256
fingerprints, public-key hashes) are 256 bits. Three shapes,
one type: a kind-tagged struct holds the active byte prefix
plus a uint8 size tag, same pattern as `crypto.Digest`.

```go
type ID struct {
    bytes [MaxSize]byte  // 32 bytes
    size  uint8
}
```

The fixed-max layout costs 16 bytes of slack for ULID/UUIDv4
and 12 bytes for KSUID — the same trade-off `crypto.Digest`
already accepted. The win: a single comparable type works as a
map key, a struct field participating in equality, and a
typed alias target. Consumers don't switch on identifier shape
at every callsite.

Identifiers shorter than 128 bits (uint64 counters) belong to
`core/epoch`. Identifiers larger than 256 bits don't fit;
those use cases — full PQ public keys (ML-DSA, ML-KEM), large
key material — are key material, not identifiers in the usual
sense, and belong in their own seams (`crypto/sign`,
`crypto/kem`) when they ship.

### Format and Parse on every subpackage

Every generator subpackage exports a `Format(id.ID) string`
that produces the algorithm's canonical encoding (Crockford
base32 for ULID, hyphenated hex for UUIDv4, base62 for KSUID)
and a `Parse(string) (id.ID, error)` (named `ParseULID` in
the ulid subpackage to avoid collision with stdlib's `time`
package patterns) that round-trips it.

`Format` returns the empty string for IDs whose size doesn't
match the algorithm's expected width — defensive shape that
prevents silent data corruption when a non-algorithm-shaped
[id.ID] flows in. `Parse` returns sentinel errors
(`ErrInvalidLength`, `ErrInvalidChar`, plus algorithm-specific
errors) for malformed input.

### Compile-time-distinct identifier types

Consumers that want compile-time distinction between identifier
vocabularies embed `ID` in a struct:

```go
type EpochID struct{ id.ID }
type AccumulatorID struct{ id.ID }

gen := ulid.New(clk, rng)
epochID := EpochID{gen.Generate()}
```

Both keep every `ID` method through promotion, remain comparable,
and will not assign to one another.

A defined type — `type EpochID id.ID` — does not work here, and
the reason is worth stating because it is the shape most callers
reach for first. A defined type inherits no methods, so
`IsZero`, `Bytes`, `Compare`, `Equal` and `String` are all lost;
and because `ID`'s fields are unexported, the defined type cannot
be constructed outside this package either. Embedding is the only
shape that survives both.

The `Generator` interface still produces `ID`; the consumer owns
the wrapping.

### Entropy via Uint64 not Read

Generators read entropy via `rand.Rand.Uint64()` (returning
uint64 by value) rather than `rand.Rand.Read([]byte)` (which
would force the slice through the interface boundary and
escape it to the heap). Generators inherit the underlying
source's `Uint64` allocation contract: zero-alloc for
`rand/seeded`, `rand/pcg`, `rand/fixed`; one alloc for
`rand/crypto` (an unavoidable cost of the `io.Reader`
indirection in `rand/crypto.Rand.Uint64`).

### Time-source efficiency for ULID and KSUID

Both ULID and KSUID generators read the wall-clock timestamp
via `clock.Clock.Now().Wall / N` rather than
`Time().UnixMilli()` / `Time().Unix()`. The `Wall` field is
unix nanoseconds directly — three layers of indirection (Now
→ time.Time construction → UnixMilli → wall/1e6) collapse to
one direct division.

ULID's 48-bit timestamp field rolls over in 10889 AD; KSUID's
32-bit second field rolls over in 2150 (Epoch + 2^32 seconds).
Pre-Unix-epoch timestamps wrap. Both boundaries are documented
as out of scope.

### Why a separate KSUID generator instead of ULID-only

ULID and KSUID solve overlapping but distinct problems:

- **Granularity**: ULID is millisecond-sortable; KSUID is
  second-sortable. ULID wins on intra-second sort precision.
- **Entropy**: KSUID has 128 random bits to ULID's 80 — more
  collision-resistant within a single second.
- **Encoding**: ULID is 26-char Crockford base32 (typo-resistant
  for human transcription); KSUID is 27-char base62 (purely
  alphanumeric, friendly to URL paths and database keys).
- **Range**: ULID's 48-bit ms timestamp covers ~10889 years;
  KSUID's 32-bit second timestamp covers ~136 years. Both
  exceed any practical horizon.

Consumers in regulated industries (gov, defense, fintech,
health) often standardize on KSUID for its alphanumeric
encoding and 128-bit entropy floor. Other consumers prefer
ULID for its millisecond granularity. Shipping both lets each
consumer pick.

## Alternatives considered

### A. `type ID string` (variable-length encoded)

Opaque, encoded form per producer.

**Rejected:** loses fixed-size guarantees. Consumers that want
`[]byte` storage layouts (databases, network protocols) have
to parse the encoded form on every boundary crossing. The
fixed-max kind-tagged shape covers ULID, UUIDv4, KSUID, and
hash-derived 256-bit identifiers in one type without parsing
overhead.

### B. Generic `Generator[T any]` interface

Each consumer parameterises by their identifier type.

**Rejected:** type parameters in Go are monomorphic at the
call site. A heterogeneous container (a registry mapping name
→ any generator) requires `any` boxing, which defeats the
seam's zero-alloc purpose. The fixed-max kind-tagged ID type
closes the boxing loophole — same constraint that drove the
shape of `crypto.Digest`.

### C. Per-concept ID types in core

Ship `EpochID [16]byte`, `RequestID [16]byte`, etc. for every
identifier concept.

**Rejected:** consumer-domain types belong in the consumer.
Core ships the primitive (`id.ID`); consumers declare their
own typed aliases. This keeps core from exploding into a
vocabulary of every domain it might serve.

### D. Receiver buffer for zero-alloc `Read`

Move the entropy buffer onto the Generator receiver so
`rand.Rand.Read(g.buf[:])` doesn't escape.

**Rejected:** breaks concurrent safety. Multiple goroutines
minting IDs through the same Generator would race on the
shared buffer. The `Uint64`-based path keeps the Generator
concurrent-safe AND zero-alloc when paired with a non-crypto
rand source.

### E. Skip the monotonic-counter generator

Don't ship a counter-shaped `id.Generator` — counters belong
to `core/epoch`.

**Endorsed.** `epoch.Counter` already provides this; a parallel
generator under `id` would force the counter into 16 bytes
unnaturally.

## Drawbacks

- Fixed-max 32-byte buffer wastes 16 bytes for ULID/UUIDv4 and
  12 bytes for KSUID. Acceptable in a foundation library; the
  same trade-off `crypto.Digest` already accepted.
- Identifiers larger than 256 bits don't fit. Use cases — full
  PQ public keys (ML-DSA, ML-KEM) — are key material in their
  own crypto seams, not identifiers.
- ULID's 48-bit timestamp field overflows in 10889 AD; KSUID's
  32-bit second field in 2150. Not guarded.
- `rand/crypto`-backed generators inherit one alloc per call
  from the underlying CSPRNG. Documented; consumers on the
  hot path use `rand/seeded` instead.
- `Format` allocates the result string for every algorithm.
  Diagnostic / serialization use; consumers storing the bytes
  directly via `id.ID.Bytes` need no conversion.
- `Format` returns the empty string for ID values whose size
  doesn't match the algorithm's expected width — consumers
  cannot distinguish "empty" from "wrong-shaped input" by the
  return value alone. The contract is documented; consumers
  asserting shape do so via `id.ID.Size`.
