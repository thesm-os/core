# RFC-0008: Page — Pagination Request and Cursor Iteration

## Summary

`Page` (request) and `Cursor[T]` (response) — the pagination
shape used by every list-returning interface so unbounded scans
are impossible to write accidentally. Plus `SliceCursor[T]`, a
generic concrete `Cursor` implementation for tests and adapters
that already have all results in memory.

## Motivation

Every list interface returning `[]T` invites unbounded scans.
The fix at the type level is to return a cursor that the caller
must drain — but the cursor shape varies wildly across consumers
today: callback-based, channel-based, error-on-Next, separate
`Err()` method.

Promoting one shape into core means every list interface across
the ecosystem composes the same way, and the interface mismatch
between adapters disappears.

## Detailed design

```go
type Page struct {
    Token string
    Limit int
}
func (Page) IsFirst() bool
func (Page) WithDefault(def int) Page

type Cursor[T any] interface {
    Seq(ctx context.Context) iter.Seq2[T, error]
    NextPage() string
    Close() error
}

type SliceCursor[T any] struct { ... }
func NewSliceCursor[T any](items []T, nextToken string) *SliceCursor[T]

type Entry[K, V any] struct { Key K; Value V }
type MapCursor[K, V any] struct { ... }
func NewMapCursor[K, V any](entries []Entry[K, V], nextToken string) *MapCursor[K, V]
```

### Page

`Page.Limit <= 0` means "use the implementation's default";
implementations may enforce their own ceiling regardless of
`Limit`. `Page.Token` is the opaque continuation cursor returned
by the previous response's `Cursor.NextPage`; empty for the
first request.

`Page.WithDefault(n)` returns a copy of the request with `Limit`
replaced by `n` when the original `Limit` is unset (≤ 0).
Implementations apply their default at the top of paginated
handlers via this helper rather than scattering ad-hoc
`if p.Limit <= 0 { p.Limit = ... }` blocks.

### Cursor consumption

Go 1.23+ range-over-func iterator with mandatory `(item, err)`
shape:

```go
for item, err := range cursor.Seq(ctx) {
    if err != nil { return err }
    process(item)
}
token := cursor.NextPage()
```

The iterator yields `(zero, err)` on mid-stream failure;
callers cannot forget the error check because range-over-func
makes it syntactically unavoidable. There is no "forgot to call
Err()" trap.

`Cursor.NextPage` stays on the cursor (not on the iterator)
because the continuation token is per-traversal metadata that
the iterator itself does not carry. Typical usage: range over
`Seq` to consume one page, then call `NextPage` to get the
token for the next request.

`Cursor.Close` releases cursor resources and is idempotent.

### SliceCursor

Wraps an in-memory slice as a `Cursor[T]`. The canonical
concrete implementation for tests, fixtures, and adapters that
already have all results in memory. Honours `ctx` cancellation
between yields. External implementations live in consumer
modules — every storage adapter that streams results from a
remote backend implements `Cursor` over its own paging
primitive.

### Entry and MapCursor

Adapters paging over a key-value store want to yield (key,
value) pairs. The Go `iter` package's `Seq2[K, V]` gives two
return values but no error channel; the `Cursor` interface
needs an error channel. The reconciliation: a typed `Entry[K,V]`
struct carries the pair as a single value, and `MapCursor[K, V]`
implements `Cursor[Entry[K, V]]`.

Consumers iterate as:

```go
for e, err := range cursor.Seq(ctx) {
    if err != nil { return err }
    process(e.Key, e.Value)
}
```

`MapCursor` is to key-value adapters what `SliceCursor` is to
list adapters — the canonical in-memory concrete implementation
for tests and fixtures.

## Alternatives considered

### A. Channel-based cursor

`type Cursor[T any] struct { Items <-chan T; Err <-chan error }`

**Rejected:** channel-based iteration burns a goroutine per
cursor for nothing on the in-memory case, requires the producer
to handle context cancellation explicitly (vs the iterator's
natural early-return), and makes the `(item, err)` interleaving
fragile under concurrent reads.

### B. Callback-based cursor

`func (c *Cursor) Each(ctx, func(T) error) error`

**Rejected:** loses the early-break ergonomics of range-over-
func. Forces every caller to explicitly return errors from the
callback to unwind the iteration; range-over-func handles this
naturally with `break`.

### C. `[]T` return + offset/limit on the request

Classic REST pagination.

**Rejected:** offset-based pagination breaks under concurrent
inserts (drift, duplicates, missed items). The opaque-token
cursor is implementation-controlled and immune to this class of
bug.

### D. Sentinel errors `ErrTokenInvalid` / `ErrLimitTooLarge`

declared in package

Pre-declare the errors paginated APIs should return.

**Rejected:** no producer in the package returns them — they
were declarations without producers. Consumers that implement
the contract declare their own sentinels; if a pattern emerges,
we promote later (non-breaking).

## Drawbacks

- Range-over-func requires Go 1.23+. Satisfied by the Go 1.26
  baseline.
- Every adapter must implement `Cursor[T]` over its native
  paging primitive — a real cost. Mitigated by `SliceCursor`
  for the in-memory case and by the contract being narrow
  (three methods, well-documented semantics).
- `Cursor` is an interface, not a concrete type. The user's
  "no interface graveyards" rule applies; satisfied by
  `SliceCursor[T]` shipping as the concrete generic helper in
  the same package.

## Open questions

None.

## Unresolved / future work

- A `MapCursor[K, V]` helper for adapters that page over
  key-value stores. Defer until a consumer needs it.
- Validation helpers (`Page.WithDefault(n int)` to apply an
  implementation default to `Limit <= 0`). Defer.
