# RFC-0010: Pool — Typed sync.Pool Wrappers

## Summary

Two typed [`sync.Pool`] wrappers — `Pool[T]` for arbitrary
values and `ResetPool[T Resettable]` for values whose state
must be cleared between uses. Plus `NewBufferPool` as the
canonical convenience constructor for `*bytes.Buffer`.

## Motivation

Stdlib `sync.Pool` operates over `any`: every `Get` requires
a type assertion at the call site, every `Put` boxes T into
an interface header. The friction is small but constant on
hot paths, and the pattern repeats across every consumer
that uses pooling. Promoting one typed wrapper into core
gives every consumer a single ergonomic shape.

The second motivation is correctness: `Pool[T]` relies on
the caller to clear T's state before `Put`. On a system
serving many tenants, one forgotten `Reset` is a silent
cross-tenant data leak — the next `Get` hands the pooled
value to a different tenant with the prior tenant's bytes
still in it. `ResetPool[T Resettable]` moves the
clear-before-cache discipline from caller to implementation,
making the leak impossible at the type level.

## Detailed design

```go
type Pool[T any] struct{ ... }
func NewPool[T any](newFn func() T) *Pool[T]
func (*Pool[T]) Get() T
func (*Pool[T]) Put(v T)

type Resettable interface{ Reset() }

type ResetPool[T Resettable] struct{ ... }
func NewResetPool[T Resettable](newFn func() T) *ResetPool[T]
func (*ResetPool[T]) Get() T
func (*ResetPool[T]) Put(v T)  // calls v.Reset() before storing

func NewBufferPool() *ResetPool[*bytes.Buffer]
```

### Pool[T]

A typed `sync.Pool` wrapper. Generic over T so consumers
don't lose type safety to `any`. The pool guarantees nothing
about which T instance `Get` returns — callers must treat
every return as potentially freshly allocated, or as
carrying stale state from a prior use.

The canonical pattern is `Get` + `defer Put`:

```go
v := p.Get()
defer p.Put(v)
// ... use v ...
```

Leaking v beyond the defer is unsafe: once `Put` returns,
the next `Get` may hand the same v to a different caller.

### Resettable + ResetPool[T]

`Resettable` is the constraint satisfied by pooled values
that carry state worth clearing between uses:

```go
type Resettable interface{ Reset() }
```

`ResetPool[T Resettable]` wraps `sync.Pool` and calls
`v.Reset()` inside `Put` before returning v to the backing
pool. The next `Get` is guaranteed to yield a cleared
instance regardless of caller discipline.

Freshly-allocated values from `newFn` are also Reset before
being returned: the `sync.Pool.New` callback may run when
the backing pool has been GC-evicted, and consumers must see
uniformly-cleared values regardless of cache hit or miss.

### NewBufferPool

`*bytes.Buffer` satisfies `Resettable` directly (it has a
`Reset()` method). `NewBufferPool` is a one-line convenience:

```go
func NewBufferPool() *ResetPool[*bytes.Buffer] {
    return NewResetPool(func() *bytes.Buffer { return new(bytes.Buffer) })
}
```

Construct one BufferPool per "shape" of allocation —
separate pools for small (~256 B) and large (~64 KiB)
buffers — to avoid retaining oversized buffers in the
small-allocation pool.

## Alternatives considered

### A. Interface-only seam (Pool / ResetPool / Buffer / BufferPool as interfaces)

Define the surface as Go interfaces and ship a `sync`-backed
implementation as a separate type or subpackage.

**Rejected:** there's only one realistic backing strategy
(`sync.Pool`). The interface layer is dead weight: no
algorithm choice to abstract over. Consumers that genuinely
want a substitute (a no-op pool for tests, a fixed-size ring
pool) wrap the concrete type in their own adapter.

### B. Single `Pool[T any]` with optional reset callback

```go
func New[T any](newFn func() T, opts ...Option[T]) *Pool[T]
func WithReset[T any](resetFn func(T)) Option[T]
```

**Rejected:** loses type-level enforcement — a consumer
could forget to wire the reset callback for a Resettable
type. The constraint `T Resettable` on `ResetPool[T]` is the
load-bearing feature; option-based wiring undoes it.

### C. Linear `Handle[T]` wrapper

Pre-`ResetPool` iterations of similar libraries used a
`Handle[T]` wrapper that called `Release` on scope exit to
return the pooled value automatically.

**Rejected:** `&Handle{...}` escapes to the heap on every
`Acquire`, turning a pool meant to eliminate allocation into
one that merely substitutes a small alloc for a large one.
Pure value-type Get/Put preserves zero-alloc on the hot
path.

## Drawbacks

- `sync.Pool` may evict cached values under GC pressure;
  `Get` then falls through to `newFn`. Documented; expected.
- `Pool` puts the clear-before-Put discipline on the caller.
  Mitigated by recommending `ResetPool` for any value that
  carries tenant- or request-scoped state.
- `Resettable.Reset` panicking propagates up through
  `ResetPool.Put`. The implementation does not catch the
  panic — a Reset panic is a bug in T, not a pool concern.

## Open questions

None.

## Unresolved / future work

- Metrics hooks (Get count, Put count, miss count) for
  observability. Defer until a consumer demonstrates the
  need.
- Bounded / non-evicting pool variants for use cases that
  cannot tolerate sync.Pool's GC-eviction behaviour. Defer
  until a consumer surfaces a real workload.
