# RFC-0006: Tag — Snapshot-Immutable Key/Value Pairs

## Summary

A `Tag` value type and `Tags` slice with lookup and immutable-
update helpers, used in place of `map[string]string` on value-
type structs that cross async-buffered, cached, or
cross-goroutine boundaries.

## Motivation

Go maps are pointer-backed. A value-type struct embedding a
`map[string]string` field carries a shared reference, not an
independent copy. Passing such a struct by value into an async
I/O path (audit buffers, metric pipelines, memoising caches)
and then mutating the map from the caller causes a data race on
the buffered writer's side — and Go maps are not safe for
concurrent read alongside a single writer (rehashing
invalidates concurrent readers).

Library code today either reinvents a `[]struct{K,V string}`
shape per consumer or accepts the race risk. Promoting the
shape into core gives every consumer a single vocabulary for
"key/value attributes that survive a value-type copy."

## Detailed design

```go
type Tag struct { Key, Value string }

func (t Tag) IsZero() bool

type Tags []Tag

func (Tags) Find(key string) (Tag, bool)
func (Tags) Has(key string) bool
func (Tags) Get(key string) string
func (Tags) With(t Tag) Tags
func (Tags) Without(key string) Tags
```

Strings are immutable in Go; a `[]Tag` slice constructed per-
event is snapshot-immutable by convention. Callers needing to
mutate must allocate a new slice — there is no shared mutable
state to leak across the boundary.

### Lookup semantics

Linear scan via `Find`, `Has`, `Get`. For the small N typical
of metric labels and structured-log attributes (≤ 16), linear
scan is faster than a hash lookup and zero-alloc. When
duplicate keys exist, `Find` / `Has` / `Get` return the first
match (first-write-wins).

### Immutable updates

`With` and `Without` return new slices; the original is left
unmodified. `With` replaces an existing key in place (preserves
length); appending if the key is absent. `Without` removes
every duplicate of the key.

### When to use Tags vs map[string]string

- **`Tags`**: every value-type struct passed by value into an
  interface whose implementation may buffer, cache, or hand off
  to another goroutine. Compliance evidence (audit events,
  usage events, evaluation runs), structured-log fields,
  metric labels.
- **`map[string]string`**: declarative control-plane state
  where mutability is part of the contract and implementations
  deep-copy on store. Kubernetes-shaped Labels and Annotations
  remain maps.

## Alternatives considered

### A. `map[string]string` everywhere

The Go-idiomatic choice for key/value data.

**Rejected for value-type-by-value scenarios:** the data race
described in Motivation is real and has bitten production
systems. The cost of `[]Tag` (linear lookup, immutable copy on
update) is tolerable; the cost of a silent data race is not.

### B. Variadic `Tags.With(t ...Tag)`

Stdlib idiom.

**Rejected:** `With` is shaped to insert one tag at a time with
replace-existing-key semantics. A variadic form would either
require the caller to construct a slice anyway (defeating the
convenience) or split into Add-many vs Replace-many variants.
The single-tag form is the common case; bulk construction uses
a literal `Tags{...}`.

### C. `TagSet` type with unique-by-key semantics

Force uniqueness at the type level.

**Rejected:** uniqueness enforcement requires either a hash
table (defeats the slice's value-type story) or scan-on-insert
(O(n²) for bulk construction). First-write-wins via `Find` is
the simpler contract; `Tags.With` provides replace-in-place
when uniqueness matters.

## Drawbacks

- O(n) lookup vs map's O(1). For small N (≤ 16) the constant
  factors favour `Tags`; for large N consumers should question
  whether they really want this shape at all.
- `Tags.With` and `Tags.Without` each allocate a new slice.
  Acceptable for cold paths (init, configuration changes); not
  for hot loops.
- Duplicate keys are permitted by the type. Tooling that
  expects unique-by-key views must dedupe at the boundary.

## Open questions

- **`Tags.Dedupe()`** — collapse duplicate keys with last-
  write-wins or first-write-wins. Defer until a consumer needs
  it.
